# 起卦规则规格

- 状态：基础不变量、起卦会话状态机与卦象确定性算法已冻结；生产映射与传统解释选择规则待确认
- 规格版本：`divination-input-v1-draft`
- 最后更新：2026-07-19

## 1. 适用边界

本文只规定三枚铜钱原始输入、爻状态、本卦/动爻/变卦的确定性数据约定。八宫、世应、纳甲、旺衰、用神和“动爻数量如何选择解释文本”等传统规则不在本文中擅自决定。

## 2. 三枚铜钱取值与概率

每次起爻包含三枚相互独立铜钱。每枚铜钱编码为 `2 | 3`，且在公平模拟中：

- `P(2) = 1/2`；
- `P(3) = 1/2`。

单次爻值是三枚铜钱之和，唯一合法范围为 6 至 9。由三枚独立铜钱自然得到：

| 总和 | 组合数 | 概率 | 名称 | 本爻阴阳 | 是否动 | 变后阴阳 |
| ---- | -----: | ---: | ---- | -------- | ------ | -------- |
| 6    |      1 |  1/8 | 老阴 | 阴       | 是     | 阳       |
| 7    |      3 |  3/8 | 少阳 | 阳       | 否     | 阳       |
| 8    |      3 |  3/8 | 少阴 | 阴       | 否     | 阴       |
| 9    |      1 |  1/8 | 老阳 | 阳       | 是     | 阴       |

禁止直接从 `[6, 7, 8, 9]` 做等概率抽取。生产随机源必须使用平台安全随机能力；测试使用可注入的固定/种子源。摇动和点击只触发一次起爻，动作强度不改变概率。

## 3. 爻位与存储顺序

- 第一次起爻为初爻，位于卦象最下方；
- 第二至第五次依次向上；
- 第六次为上爻，位于最上方；
- 内部数组始终按初爻到上爻存储；
- 数组索引 0 对应初爻，索引 5 对应上爻；
- UI 从上向下画卦时可以对副本倒序遍历，不得原地反转领域数组。

每一爻至少保留 `{ position, coins, value }`。其中 `position` 为 1 至 6，`coins` 是长度恰为 3 的原始数组，`value` 必须等于三项之和。衍生阴阳和动静可以重算，不替代原值。

## 4. 阴阳编码

实现层采用明确、非传统含义的二进制约定：

- `Yin = 0`；
- `Yang = 1`。

爻值到本爻编码：6/8 → 0，7/9 → 1。变爻编码：6 → 1，9 → 0，7/8 保持本爻编码。类型应使用字面量联合或枚举封装，禁止在业务代码散落裸数字判断。

二进制编码只是内部数据约定，不代表对古籍次序或象数体系的解释。

## 5. 上下卦拆分

给定按初爻到上爻存储的六位阴阳数组 `lines[0..5]`：

- 下卦取 `lines[0..2]`，仍按下爻到上爻排列；
- 上卦取 `lines[3..5]`，仍按下爻到上爻排列。

八种技术位型使用 `trigram-pattern-{bottomToTopCode}` 稳定标识；传统八卦内容由显式位型映射得到。64 卦必须由“上卦稳定 ID + 下卦稳定 ID”的显式映射得到，不得假定数组位置或二进制值等于传统卦序。正式映射表仍需来源核验后导入，详见 `HEXAGRAM_SPEC.md`。

## 6. 本卦、动爻与变卦

- **本卦**：把 6/8 视为阴、7/9 视为阳得到的六爻阴阳结构；
- **动爻**：原始值为 6 或 9 的爻，位置以 1 至 6 表示并按升序保存；
- **变卦**：逐爻执行 6 阴变阳、9 阳变阴，7 阳和 8 阴保持不变后得到的六爻结构。

这三个结果只由六次原值决定，不受问题文本、分类、时间、摇动力度、UI 动画、AI 或解释规则影响。

## 7. 动爻数量处理入口

领域计算先生成统一的 `InterpretationContext`，至少包含本卦、变卦、动爻位置、动爻数量和 `rulesetVersion`。随后调用版本化的 `MovingLineSelectionPolicy` 选择哪些经文/规则作为解释依据。

必须分别保留以下入口：

- `movingLineCount = 0`：无动爻入口；
- `movingLineCount = 1`：一爻动入口；
- `movingLineCount = 2..5`：多爻动入口；
- `movingLineCount = 6`：六爻全动入口。

本模块**不规定**每个入口应取卦辞、哪条爻辞或其他特殊文本。该选择属于存在传统差异的规则，必须在可靠来源、采用体系和固定案例确认后，以独立规则版本实现。不得在组件中临时判断。

## 8. 会话状态边界（模块二实现）

状态机固定为 `draft → collecting → complete → locked`，并用显式命令实现追加、撤销、恢复、重置与锁定。提示词中的 `idle/casting/completed/cancelled` 仅为建议命名，不替代本规格及数据字典已经确认的状态名。

- 一次追加只能增加一爻，最多六爻；
- 恢复不得重新生成已保存爻；
- 撤销保存可恢复的最后一爻，不改写更早原值；
- 锁定只允许在六爻完整时发生；
- 锁定后任何修改命令必须失败；
- 会话快照保存 Schema 版本和规则版本。
- `complete` 表示已产生六爻、等待显式确认锁定；该状态已经只读，不能撤销或重置；
- 每个追加命令携带调用方看到的预期爻数，陈旧命令在读取随机源前拒绝；Application Service 同时拒绝同一会话的并发变更；
- 撤销的爻保存在 `redoLines`，显式恢复直接使用该原值，不重新读取随机源；产生新爻或重置会清空恢复栈。

状态机细节在“起卦核心”模块通过纯 TypeScript 和测试冻结。

## 9. 规则版本字段

所有领域输入/结果至少携带：

- `inputSchemaVersion`：原始铜钱记录结构版本；
- `divinationRulesetVersion`：爻解析、本卦/变卦计算规则版本；
- `interpretationRulesetVersion`：动爻选择与解释规则版本；
- `contentVersion`：引用文化内容版本。
- `randomAlgorithmVersion`：产生原始铜钱的随机算法/适配器版本。

版本是不可变标识，不使用“latest”落库。旧记录保留原版本与结果快照。

模块二采用 `divination-input-v1-draft` 作为当前输入 Schema 与基础起卦规则标识，采用 `expo-crypto-random-byte-lsb-v1` 记录正式随机算法。正式随机源为 `expo-crypto.getRandomBytesAsync`；每枚铜钱读取一个安全随机字节并取最低位，256 个字节值恰好各有 128 个映射为 2/3，不使用同步开发降级或 `Math.random()`。平台安全随机不可用时显式返回 `SECURE_RANDOM_UNAVAILABLE`，不自动重抽；后续平台适配器可替换该端口，但必须使用新的不可变算法版本。

## 10. 尚未确认的传统规则

以下仅列缺口，不代表采用任何体系：

- 八卦中文名称、符号内容采用的固定来源版本与人工审核；
- 64 卦上/下卦组合映射、中文规范化、文王卦序的固定来源版本与发布授权；
- 无动爻、一爻动、多爻动、六爻全动时选择卦辞/爻辞的规则；
- 六爻全动是否及何时使用特殊文本；
- 八宫、世应、纳甲、六亲、六神；
- 干支历换日边界、时区与历法实现；
- 月建日辰、旬空、生克冲合、旺衰；
- 用神选择、动变分析、规则优先级和冲突处理。

确认每项时必须记录体系名称、原始/现代来源、版本、授权、审核人、日期、适用边界和固定案例。

## 11. 测试要求

- 三枚铜钱原值与合计一致；
- 所有非法铜钱数、数组长度、爻值和会话顺序被拒绝；
- 固定随机源得到固定会话；
- 大样本统计只用于检验实现偏差，不替代组合概率证明；
- 穷举 4⁶ = 4096 种爻值状态，验证本卦/变卦合法、动爻 0..6、6/9 翻转、7/8 保持；
- 相同输入和规则版本做深度相等比较；
- UI 倒序渲染不改变领域数组。
